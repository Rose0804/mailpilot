# 事件抽取与任务编排

## 产品问题

邮箱可以保存大量信息，却不会自动形成可执行的时间表。用户真正需要的是：

- 找出不同账号里的会议、截止日期、出行和承诺。
- 知道每个事实来自哪封邮件，以及 Agent 有多确定。
- 把事实变成任务，并表达“先完成什么，再完成什么”。
- 看到时间重叠，而不是在自然语言总结中手动比对。

## 三层模型

### `MailEvent`

事件是从邮件或附件中提取出的事实。它可以是会议、截止日期、出行、提醒或承诺。

事件必须保留：

- `sources`：账号、邮箱、邮件标识和原文证据。
- `confidence`：Agent 对抽取结果的置信度。
- `status`：`proposed`、`confirmed` 或 `dismissed`。
- 可选时间字段：不确定时为空，不由系统猜测。

### `OrchestrationTask`

任务是需要用户或后续连接器完成的行动。它可以关联多个事件和邮件，并用 `dependencyIds` 关联前置任务。

`accountIds` 保存任务涉及的所有邮箱账号。一个任务可以同时引用工作邮箱和个人邮箱，不能只依赖当前选中的邮箱文件夹。

### `ScheduleOverview`

时间表是确定性派生视图：

- 事件使用 `startAt`、`endAt` 或 `dueAt` 生成时间块。
- 任务使用 `dueAt` 和 `estimatedMinutes` 反推工作区间。
- 时间块按 ISO 时间排序。
- 两个有明确区间的时间块重叠时生成 `conflict`。

它不保存模型的思维链，也不把模型的自由文本当作排程真相。

## Agent 工作流

```text
用户：帮我安排这周需要跟进的事情
    ↓
list_accounts
    ↓
search_messages / search_attachments
    ↓
get_message / get_attachment_text
    ↓
record_mail_event × N
    ↓
create_task × N
    ↓
list_schedule
    ↓
返回时间表、冲突、不确定项和来源
```

每个来源证据必须能在已索引邮件的发件人、主题、摘要或正文中找到。邮件内容和附件内容始终是不可信数据，只能作为事实来源。

## API

```text
GET /api/planning/overview
GET /api/planning/events
GET /api/planning/tasks
```

查询参数：

```text
accountIds=work,personal
dateFrom=2026-09-15T00:00:00Z
dateTo=2026-09-21T23:59:59Z
```

桌面端的 `NEXT UP` 区域展示接下来的时间块、来源账号、任务依赖和冲突。Inspector 的 `TASK GRAPH` 展示任务关系。

## 当前边界

- Agent 可以提取和编排，但不会自动写入系统日历。
- 发送邮件、回复、删除和批量移动仍需要 Policy 与人工审批。
- 事件去重、自然语言日期的多地区解析、重复日程和日历双向同步属于后续能力。
